1. What the three tables actually hold

Your memory.db has three tables:

  • CONVERSATIONAL_MEMORY — 5 rows. The literal transcript: thread_id, role (user/assistant), content, timestamp. This is history in order, exactly as it was said. That's the five lines show_memory.py printed.
  • CONVERSATION_VECTORS — 5 rows. The same five turns, stored a second way. Each row is content plus an embedding: a list of 1536 floating-point numbers. An embedding is what an embedding model produces when you hand it a piece of text — a point in 1536-dimensional space, positioned so that text with similar meaning lands nearby. "I'm allergic to peanuts" and "avoid nuts for me" sit close together even though they share almost no words.

Why store the same turns twice? Because the two shapes answer different questions. The transcript table answers "what were the last N turns?" — ordered, exact, cheap. The vector table answers "which past turn is relevant to what the user just said?" — you embed the new message, compare it against all stored embeddings, and take the nearest ones. That comparison is why it's called semantic search rather than keyword search.

  • SEMANTIC_MEMORY — 7 rows. Not conversation at all — standalone facts about the world, also embedded so they can be searched the same way. Here they are in full:
  1. Trail mix almost always contains peanuts and other nuts.
  2. Peanut butter energy balls are made from oats, honey and peanut butter. They contain peanuts.
  3. Sunflower seed butter is the usual substitute for people who must avoid peanuts.
  4. Edamame is steamed young soybeans: high in protein, naturally peanut-free.
  5. Rice crackers (senbei) are a common Taiwanese snack; check labels, as some are coated…
  6. Pineapple cake is a Taiwanese specialty of pineapple jam in buttery pastry…
  7. A severe peanut allergy can cause anaphylaxis. Strict avoidance is the only reliable…

Notice this is a curated little knowledge base aimed squarely at the scenario: which snacks hide peanuts, what to substitute, what's safe, and what's local to Taipei. The "seven semantic rows" are those seven facts.

So the phrase "the allergy is stored in two forms": it's in CONVERSATIONAL_MEMORY/CONVERSATION_VECTORS as something the user said, and in SEMANTIC_MEMORY as a fact about the world (row 7 — anaphylaxis, strict avoidance).

2. What run_turn does, line by line

def run_turn(user_msg: str) -> str:

Defines a function taking one string, user_msg, and returning a string. The : str and -> str are type hints — documentation for humans and editors; Python doesn't enforce them at runtime.

    messages = [
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user", "content": user_msg},
    ]

Builds the conversation to send to the model. The Chat Completions API doesn't take a blob of text — it takes a list of messages, each a dict with a role and content. system is the standing instruction ("You are SnackBot, a snack-recommendation assistant."); user is what the human just said. The list is the model's entire world for this call.

    return call_llm(messages).content

call_llm posts that list to client.chat.completions.create(...) and returns response.choices[0].message — the model's reply object. .content pulls the text out of it.

The thing to notice: messages is rebuilt from scratch on every call, out of two constants and the current input. Nothing from memory.db is ever put into that list, and nothing from the reply is ever put back into memory.db. The file is a stateless function that happens to sit next to a full database.

The two ways to know how many tokens you used

Way one — ask the API afterwards. Every response object comes back with a usage field:

response.usage.completion_tokens  # what it actually billed for output

This is ground truth. It's what appears on your invoice. But it only exists after the call has completed and the money is spent.

Way two — count the text yourself. That's what meter.py does. tiktoken is the same tokenizer OpenAI's models use; you hand it a string, it hands back the list of token IDs, you take the length. No network, no cost, no API key needed.

Why this course picked way two

Look at where you're headed. Rounds 2–5 are all variations on one question: how much stuff do I stuff into the prompt? Deterministic memory says "inject the last N turns and the top-K semantic hits, every single turn." That makes the prompt bigger, and bigger prompts cost more. The entire trade-off you're being asked to reason about lives in the input token count.

Now suppose you want to ask: "What would it cost if I injected all 5 conversation turns plus 7 semantic facts on every turn?" With response.usage, the only way to find out is to make the call and pay. With local counting, you can build the prompt string, count it, price it, and decide — without sending anything. That's what "compute the cost before you spend it" means. It turns cost from a thing you observe into a thing you can design against.

There's a second reason. Not every LLM-adjacent operation returns a usage field you care about, and you may want to meter text that never becomes a request at all — a memory row you're deciding whether to include, a retrieved chunk you're deciding whether to trim. A local counter works on any string. response.usage only works on completed requests.

What you give up — and it's real

Local counting is an estimate, and it under-reports in three specific ways:

  1. Message overhead. The API doesn't send your text raw; it wraps each message with role markers and separators. Those are a handful of tokens per message. meter.py joins the contents with "\n" and counts that, so it misses the wrapper — a few tokens per call, more as your message list grows.
  1. Reasoning tokens. On reasoning-capable models, the provider may bill output tokens the model generated while thinking that never appear in .content. Your meter counts the visible reply only. If those exist, the real output count can exceed yours substantially.
  1. Prompt caching. If a provider serves part of your prompt from cache at a discount, your local count says you paid full price. Your estimate is high, the invoice is lower.

For comparing designs — the entire purpose of this course — local counting is not just adequate, it's better: it's consistent, free, and available before you commit. The ? is a parameter placeholder. You write the SQL with a hole in it, and pass the value separately:

conn.execute("... WHERE thread_id = ? ORDER BY id", (THREAD_ID,))

Two arguments: the SQL string, and a tuple of values to fill the holes, left to right. One ? → one-element tuple. The INSERT has three ? and gets a three-element tuple in matching order.

The tempting alternative is string formatting:

conn.execute(f"... WHERE thread_id = '{THREAD_ID}' ORDER BY id")   # don't

That builds one finished string and hands it to the database. It works — right up until the value contains a quote.

Why it breaks. Suppose a thread id were o'brien. The f-string produces:

WHERE thread_id = 'o'brien'

The quote closes the string early, brien' is now stray syntax, and the query fails. That's the benign case.

The malicious case. Now suppose a value comes from a user, and they submit:

x' OR '1'='1

The f-string produces:

WHERE thread_id = 'x' OR '1'='1'

'1'='1' is always true, so the WHERE matches every row — every thread, every user. Your prompt now contains other people's conversations. With a ; and a second statement, the same trick reaches DROP TABLE. This is SQL injection, and it's been the top-ranked web vulnerability for two decades.

Why ? is immune. The value never becomes part of the SQL text. SQLite parses the statement first — with the hole still in it — and produces a compiled plan where "compare this column against a value" is already fixed as the structure. Then the value is bound into that slot as data. A quote in the data is just a quote character; there's no parser left to confuse. The string x' OR '1'='1 becomes a search for a thread literally named x' OR '1'='1, which matches nothing.

Structure comes from your code, values come from the tuple, and the two never mix.

A few practical notes:

  • The trailing comma matters. (THREAD_ID,) is a one-element tuple; (THREAD_ID) is just a parenthesized string, and execute would raise an error about parameter count. Easy to trip on.
  • Placeholders are for values only. You can't write SELECT * FROM ? — table and column names are structure, not data.
  • There's a named form too: WHERE thread_id = :tid with {"tid": THREAD_ID}. Same protection, more readable when there are many parameters.

In this codebase THREAD_ID is a hardcoded constant, so nothing dangerous can reach it today. Using ? anyway is the habit that matters — the day a thread id starts coming from a request header, the code is already correct.
